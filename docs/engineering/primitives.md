# Agent primitives

Skills, agent personas, instructions, hooks and memory are code, not documentation: they are
versioned, packaged, checked and reviewed. This standard is adapted from the ML in PL agentic
coding workshop (ktfish.github.io), *Agentic SDLC* and microsoft/apm; decision in
[ADR-0016](../decisions/0016-apm-for-agent-primitives.md), contract in
[SPEC-005](../../.ai/specs/SPEC-005-agentic-primitives.md).

## Packaging (APM)

| Piece | Role here |
| --- | --- |
| `.apm/skills/<name>/` | The only place a repository skill is edited |
| `apm.yml` | Package manifest: name, `targets` (`claude`, `codex`), dependencies |
| `apm.lock.yaml` | Exact resolved state with content hashes; committed |
| `.agents/skills`, `.claude/skills` | Generated by `apm install`; never edited by hand |
| `apm_modules/` | Transitive dependencies; gitignored |

Edit the source, run `apm install` (`pip install apm-cli`), commit source, deployments and lock.
`scripts/check_repository.py` fails when a deployment differs from its source, so the gate does not
need `apm`; `apm audit` is the stricter check when it is installed. Pin external packages to a tag
or commit (`owner/repo#v1.2.0`); run `apm prune` after removing one. Skill layout: `SKILL.md` plus
optional `scripts/`, `references/`, `assets/`, `examples/`.

## Description is a contract

Frontmatter is loaded every session; the body only when used. Write `Use when ...`, add a
negative case when skills could overlap, and treat a changed description as a breaking change.
Keep the body under 200 lines (checked); move templates and long rules to `references/` or `assets/`.

## Which primitive?

| Knowledge | Primitive |
| --- | --- |
| Rule for specific files or directories | instruction |
| Needs specialist expertise, a different model or a restricted toolset | agent persona |
| Cuts across files, needs a decision framework | skill |
| Repeatable multi-step process | prompt or workflow |
| Decision, trade-off or history | memory, ADR |
| Feature with success criteria | spec |
| Automatic response to an event | hook |

Prefer a deterministic check (gate, hook, `scripts/check_repository.py`) over any instruction
that asks a model to remember a rule.

## Patterns to use

| Pattern | Use it to | Prevents |
| --- | --- | --- |
| Split (R1) and orchestrator facade (S3) | break a monolith into specialists behind one entrypoint | god module |
| Conditional dispatch (B2) | load only the branch the request needs | all-branches-loaded |
| Lazy asset (C1) | keep templates in `assets/`, read on demand | eager bloat |
| Persona preload (C2) | scope a role, instructions and tools (read-only reviewer) | unprompted drift |
| Thread spawn (C3) | run noisy work in a child and return a receipt | fan-out in one context |
| Deterministic tool bridge (S7) | state facts only from a command's result | toolless assertion |
| Validation decorator (S4) | halt on a non-zero exit | wrapping without blocking |
| Adversarial review (A7) | judge in a fresh context | self-approval |

A child receives a telegraphic brief (role, exact paths, commands, constraints) and returns a
small receipt, for example `{status, artifact_path, error_digest}`. Never substitute a model's
judgement where a tool can check.

How Yulius already applies them: the delivery pipeline is an orchestrator facade; the independent
review is a read-only persona with a fresh context; gates are deterministic tool bridges; the
step plan is a plan memento.

## Instrumentation audit

For a repository whose conventions live in people's heads:

1. List the conventions (setup, logging, structure, release, review, research or decision log).
2. Classify where each lives: heads, code, literature, guidelines, tooling, docs. Only code in the
   context window is visible to an agent.
3. Rank by failure cost: critical (blocks progress or corrupts results), high (hurts
   reproducibility), medium (rework), low (style).
4. Map each to a primitive type using the table above.
5. Write the starter set, highest cost first, small; improve it after every review.

`infra-bootstrap` runs this for each onboarded project.
