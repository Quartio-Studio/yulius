# SPEC-144: `pulls.e2e.ts` waits on conditions, and a failed read keeps the real chips

Status: in-progress
Date: 2026-10-15
Owner: Yulius task #133 (part of task #118, SPEC-138 lanes)
Scope authorization: the person's request (task #133). Fix GitHub issues #438, #444, #461, #469
and #415, all in `e2e/tests/pulls.e2e.ts` (SPEC-104, SPEC-108, `store.js` `loadPulls`).
Reproduce each flake under CPU load, fix its cause in the test or in the read scheduler, and show
`pulls.e2e.ts` passing 20 consecutive runs under load, with no retries and no sleeps. Create no
new GitHub issue.

## Goal

Every test in `pulls.e2e.ts` checks what it claims, whatever the machine's speed: it waits on a
state the UI really reaches, never on a wall-clock window. A failed later read of the Git
overview is proven to keep the chips an earlier read on the same page showed.

## Context

- **#438.** `chipsAfterRead` waited for the first `.tl-pr-chip` to be visible and then read
  every chip's text. The harness reads text as `innerText` (`read-semantics.js` `textOf`).
  Sidebar rows have `content-visibility: auto` (`styles.css` `.task-row`, PERF), so a row
  inserted since the last rendering update is skipped. Its chips already have a box, which is
  enough for `toBeVisible`, but their `innerText` is `""`.
  - Reproduced against the real UI with Playwright: 3 of 10 page loads read `["","",""]`, the
    issue's capture. In plain Chromium, a row inserted and read in the same task (or the next
    evaluate) reads `""` with a 17 px tall box, and reads `"PR #221"` after two frames.
  - Under load, frames lag behind the DOM, so the window between insertion and paint grows.
- **#461.** "a stored value that is an object is ignored and the overview fills the rows" starts
  with the same `seen = await chipsAfterRead(browser)`.
  - `readJson` turns the object into `[]` (PRC-004), so the held reload shows no chip.
  - The only assertion load can fail is the last one, `toHaveText(seen)`, when `seen` holds the
    empty labels of #438. This is the issue's failing assertion. It was not kept in the original
    trace and is recorded here.
- **#444.** "announcements within the gap make one read when it has passed" runs with
  `pullgap=1500` on real time. Under load the test can reach the announcements more than 1.5 s
  after the first read started. Then:
  1. The first announcement reads at once (PRL-004).
  2. The next two arrive during that read and ask for one more read after it (PRL-005).
  3. That read comes one gap later.
  4. A count taken more than 1.5 s after the chip turned merged includes it: `expected 3 to be
     2`, the issue's exact failure.
  - Reproduced deterministically by holding the test 1.6 s before the announcements and before
    the final count (a throwaway probe).
  - The scheduler is right. The test depends on wall time.
- **#469.** Already fixed on `dev` by 43731493 (PR #490). The test sets `signedIn = false` and
  navigates by address in the same evaluate, and never clicks a link that the sign-out can
  remove. Closed with a comment that names the commit.
- **#415.** `loadPulls`'s catch keeps the chips of an earlier read on this page and drops only
  chips seeded from storage (PRC-003). No test covers the "keeps" branch, and the mock cannot say
  that a GET failed on purpose, so a "chips still shown" assertion would pass vacuously.
- **CPU load.** Normal-priority busy loops do not reproduce these flakes: 20 runs of the
  unchanged file passed under 12 and then 40 burners on 12 cores, two `npx e2e run` lanes at
  once. The scheduler's fair share keeps Chromium's frames going. The reproductions above force
  the two mechanisms directly instead.

## Acceptance criteria

- `chipsAfterRead` waits on labels (non-empty text of every chip), not on the first chip's box.
- The #444 case counts reads on the manual clock: `before` during the gap, `before + 1` after
  `advanceClock(1500)`. The 1.6 s stalls of the reproduction no longer change the result.
- The #415 case passes, and fails with `loadPulls`'s catch changed to clear without condition.
- `pulls.e2e.ts` passes 20 consecutive runs under load: two lanes of 10 runs at once, with CPU
  burners. No retries or sleeps are added.
- #438, #444, #461 and #415 are closed after the merge with a comment that names the PR. #469 is
  closed as already fixed by 43731493 (PR #490).

## Test plan

- Reproductions, kept out of the repository: the Playwright CPU-throttling script for #438/#461,

- `npx e2e run tests/pulls.e2e.ts` alone, then 20 runs under load

## Decisions

- **#444: inject the clock, rather than take `before` later or count only announcement reads.**
  Both alternatives still need the announcements to land within 1.5 s of a read on the host's
  clock. A loaded host can break that, which is how the test failed.
  - The store already takes `pullGapMs` from the transport. A clock beside it is the same seam,
    and production keeps the real timers.
  - Recorded as [ADR-0118](../../docs/decisions/0118-the-mock-drives-the-pull-request-read-clock.md).
- **#438: fix it in the test, not by dropping `content-visibility`.** The skipped rendering is a
  deliberate PERF choice (long sidebars). People see the text from the first frame. Only a reader
  that runs between insertion and paint sees `""`.
- **#415: two failed reads, then a repaint signal.** A failed read is counted when the mock
  answers, before the store handles it. Reads never overlap (PRL-005), so a second failed read is
  asked for only after the first one's `finally`, which comes after its catch. A rename shown
  after that proves the coalesced sidebar repaint ran after the catch.
- **#469 needed no change.** It is closed as already fixed, citing the commit.
